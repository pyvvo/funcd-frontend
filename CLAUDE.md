# CLAUDE.md

Guidance for Claude Code in this repository. Read it before writing any code.

## The rule: new code must match the existing code

- New code must have the same shape and behavior as the code already in this repository: file layout, naming, component structure, styling, stories and tooling. Before writing, open one or two files of the same kind from [Model files](#model-files) and copy their shape.
- Do not introduce a new convention on your own: no new patterns, libraries, folder layouts, naming styles, state-management approaches, test frameworks or lint rules.
- Only the user can change a convention. If you think one should change, explain why and wait. Propose a new way of writing code only after the user explicitly asks for it.
- If a task needs something the repository has no pattern for, propose a shape based on the closest existing pattern and wait for the user's approval before writing it.
- Bug fixes are welcome, but write the fix in the existing shape.
- Where the existing code is inconsistent, follow the most recent files and the majority pattern. Do not clean up unrelated code, commented-out code or old lint comments unless asked.
- Keep existing names, including misspelled ones (`loadWorflows`, `flowMetadaForm`, `customHandlechange`), because other code depends on them.
- Write identifiers, comments and UI text in English.

## Repository

- Yarn 4 workspaces under `packages/`. Use `yarn`, never npm. The toolchain is Vite+ (`vp`: Vite, Rolldown, Vitest, Oxlint, Oxfmt) with TypeScript 7.
- `packages/ui` (`@humaapi/ui`): the React component library, shown in Storybook 10. It is built on Mantine 9, react-hook-form, ECharts 6 and @xyflow/react. Most work happens here.
- Mantine docs for LLMs: the index is `https://mantine.dev/llms.txt`, and each component has a Markdown page at `https://mantine.dev/llms/core-<component>.md` (for example `core-textarea.md`) with its props, types and examples. `https://mantine.dev/llms-full.txt` holds everything in one file. Read these before using a Mantine API you are unsure of.
- `packages/lib` (`@humaapi/lib`): the HTTP SDK generated by hey-api (`src/client/*.gen.ts`), plus small utilities. Never edit generated files by hand; regenerate them with `yarn lib gen:sdk`.
- `packages/codegen` (`@humaapi/codegen`, private): holds the hey-api generator and its config, which `yarn lib gen:sdk` runs. It pins TypeScript 5 because hey-api needs TypeScript's JS API, which TypeScript 7 removed. Keep TypeScript 7 everywhere else.
- `packages/control-plane-ui`: the real app (workflows and node registry). `packages/example`: a demo app.
- The apps use the built `dist` of `ui` and `lib`. Run `yarn ui build` or `yarn lib build` before an app can see a change.
- `scripts/` holds an old OpenAPI codegen CLI (`yarn codegen:schema`) whose output folders no longer exist.

- Before you finish a change in `packages/ui`, run `yarn ui tsc` and `yarn ui lint`. Both must pass.
- `yarn ui typecheck` only checks type-test files, and there are none. Use `yarn ui tsc`.
- There are no unit tests. Reactive-field stories have `play` interaction tests, which run in the Storybook UI.
- The lefthook pre-commit hook runs `vp lint --fix` and `vp fmt` on staged files. It is the repository's only automatic enforcement; do not add Claude Code hooks for linting or formatting.

## Formatting and lint

- Oxfmt (`fmt` in the root `vite.config.ts`): single quotes, semicolons, no trailing commas, `bracketSameLine`, 80 columns, 2-space indent.
- Oxlint (`lint` in the root `vite.config.ts`) is type-aware, so TypeScript errors are lint errors. `no-unused-vars`, `no-explicit-any` and `ban-ts-comment` are off. `prefer-const` and `no-var` are errors. `react-hooks/exhaustive-deps` is on.
- Do not add file-top `/* oxlint-disable ... */` or `/* eslint-disable ... */` headers. Only files from the first commit (November 2024) have them, and 190 of the 203 directives in `packages/ui/src` have no effect.
- When the linter reports a line that must stay as it is, put `// oxlint-disable-next-line <rule>` directly above that line. In practice this is `react-hooks/exhaustive-deps` above a dependency array.

## TypeScript and imports

- TypeScript runs in `strict` mode. `any` is allowed and used, mostly through `JSONData` (`Record<string, any>`).
- In `packages/ui`, the `@/` alias points to `src/`. Use it to import from another top-level folder (`@/molecules`, `@/reactive-form`, `@/types`, `@/utils`), and use relative paths inside the same folder. The apps use relative imports only.
- Write imports as one block: package imports in alphabetical order (`@/…` sorts first), then relative imports in alphabetical order. No tool enforces this, so keep the order by hand.
- Import types like values: `import { FC, ReactNode } from 'react'`. Use `import type` only for Storybook types. Components never import React as a default.
- Use string unions, not enums. Use `satisfies Record<Union, Handler>` to keep handler maps complete.

## Naming

- Files and folders: kebab-case, with a dotted role suffix when the file has a role: `card.tsx`, `card.module.css`, `card.stories.tsx`, `toolbar.types.ts`, `workflow.store.ts`, `app.routing.tsx`. Hooks live in `use-<name>.tsx` files. `HmTableRow.tsx`, `Button.module.css` and `useCreateNodeForm.ts` are exceptions; do not copy them.
- Components: PascalCase. Prefixes are mixed (`HMChart`, `HmTable`, `HmFlowHeader`, `FlowCard`); follow the components in the same folder.
- Interfaces: `I` prefix (`IFlowCard`, `IReactiveField`). Type aliases: PascalCase, usually with a `Type` suffix (`InputType`, `RowType`). Custom props of a reactive field: `<Name>CustomProps`.
- Generics: `T` plus a name (`TFormValues`, `TRow`, `TFieldProps`).
- Variables, functions and module-level constants: camelCase (`fieldMap`, `nodeWidth`, `defaultActions`). No UPPER_SNAKE_CASE.
- Callback props: `onX` (`onDelete`, `onSubmit`). Handlers declared inside a component: `handleX`. Boolean props: `withX` (`withHeader`). Boolean locals: `isX` or `hasX`.

## Git

- Commit messages: lowercase `type(scope): imperative summary` (`feat`, `fix`, `chore`, `refactor`). Add a scope only to name a package (`fix(ui): ...`). PRs are squash-merged, so the PR title becomes the commit subject, with `(#NN)` appended.
- Branches: `<type>/<kebab-case>` (`feat/...`, `fix/...`, `chore/...`).
- Recent PR descriptions use `## Summary` and `## Verification` sections.
- Commit or push only when the user asks.
